# 반론 근거 점수와 과거 실패 대조

두 도구 모두 **정해진 규칙으로 계산하는 코드**입니다. 학습하거나 스스로 나아지지 않습니다. 사람의 판단을 대신하지 않으며, GATE 1·2·3은 그대로 사용자가 결정합니다.

## 반론 근거 점수

`scripts/score-challenge.mjs` 는 `hb-agent` CHALLENGE 판정 옆에 붙일 점수를 계산합니다.

```bash
node scripts/score-challenge.mjs --input 반론결과.json
node scripts/score-challenge.mjs --input 반론결과.json --json
```

### 이 점수가 뜻하는 것

**반론 검증이 근거를 얼마나 갖췄는지**를 잽니다. 야마가 옳은지, 기사 가치가 있는지를 재지 않습니다. 그래서 탄탄한 근거로 무너진 `COLLAPSES` 는 100점이 나올 수 있고, 근거가 빈약한 `SURVIVES` 는 낮은 점수가 나옵니다.

- 체크 6을 자동으로 통과시키거나 탈락시키지 않습니다.
- 10체크의 100점 환산 점수에 더하지 않습니다.
- 판정(`SURVIVES`, `WEAKENED`, `COLLAPSES`)을 바꾸지 않습니다. 규칙과 어긋나면 알리기만 합니다.
- 입력을 사람이나 AI가 적으므로, 입력이 틀리면 점수도 틀립니다. 도구는 입력한 내용이 진짜인지 확인하지 못합니다.

### 계산 규칙

| 축 | 배점 | 계산 |
|---|---|---|
| 반론 출처 | 30 | 확인된 반론 중 가장 높은 계수 × 30. 계수는 `T1+` 1.0, `T1` 0.9, `T2` 0.6, `T3` 0.3이고, 간접 반론은 0.7을 더 곱합니다. |
| 수치 재현 | 30 | 재현을 확인한 수치 비율 × 30 |
| 거시 변수 통제 | 25 | 업종 템플릿의 변수와 입력한 변수 중 통제를 확인한 비율 × 25 |
| 비교 기준 | 15 | 기간·단위·범위가 모두 같은 직접 비교의 비율 × 15 |

- **확인된 반론**은 티어, 주소, 발행일이 있고 본문을 열어 본(`body_read: true`) 것만 칩니다.
- **반론을 못 찾은 경우**: 반대 방향 검색을 2건 이상 기록했으면 0.4 × 30점이고, 기록도 없으면 0점입니다. 못 찾았다는 사실이 반론이 없다는 증거는 아니므로 만점을 주지 않습니다.
- **재현을 확인한 수치**는 `reproduced: "match"` 이면서 성격 태그(`실적`, `전망`, `계획`, `중간집계`, `목표`)와 출처 주소가 있는 것입니다.
- **통제를 확인한 변수**는 `controlled` 와 출처 주소를 갖췄거나, `not_applicable` 과 이유를 적은 것입니다.
- **해당 없는 축은 뺍니다.** 수치나 직접 비교가 없으면 그 축을 빼고 남은 배점으로 100점 환산합니다.
- 등급은 80점 이상 `근거 충실`, 50점 이상 `보강 필요`, 그 아래 `근거 부족`입니다. 배점과 계수, 등급선은 합리적이라고 보는 값을 정한 것이며 실제 기사 데이터로 검증한 값이 아닙니다. 코드 맨 위 상수에서 고칠 수 있습니다.

### 경고 코드

| 코드 | 뜻 |
|---|---|
| `VERDICT_RULE_CONFLICT` | 야마의 근거보다 최신이고 직접적인 반론이 있는데 `COLLAPSES` 가 아닙니다. |
| `WEAKENED_NO_SCOPE` | `WEAKENED` 인데 좁힐 범위가 없습니다. |
| `SURVIVES_NO_REASON` | `SURVIVES` 인데 남는 이유나 출처가 없습니다. |
| `COLLAPSES_NO_SOURCE` | `COLLAPSES` 인데 확인된 반론 출처가 없습니다. |
| `NUMBER_MISMATCH` | 수치가 원문과 다릅니다. 고치기 전에 쓰면 안 됩니다. |
| `NUMBER_UNCHECKED` | 재현 확인, 태그, 출처 중 빠진 것이 있습니다. |
| `COUNTER_NOT_COUNTED` | 본문 미열람 등으로 점수에 넣지 않은 반론입니다. |
| `NO_COUNTER_FOUND`, `NO_COUNTER_SEARCH` | 확인된 반론이 없습니다. |
| `MACRO_UNCONTROLLED` | 통제 근거가 없는 거시 변수입니다. |
| `BASIS_MISMATCH` | 기간·단위·범위가 어긋난 비교입니다. |
| `INDUSTRY_NOT_IN_TEMPLATE`, `INDUSTRY_UNKNOWN` | 업종 템플릿으로 대조하지 못했습니다. |

## 과거 실패 대조

`scripts/check-failure-patterns.mjs` 는 사람이 적은 실패 로그와 새 후보를 대조해 비슷한 점을 알립니다.

**메타 러닝이 아닙니다.** 모델을 학습하지 않고 패턴을 스스로 찾지도 않습니다. 업종, 실패 유형, 지표, 기업, 문장이 겹치는 정도를 정해진 규칙으로 세는 대조 도구입니다. 기록이 쌓이면 대조할 대상이 늘어날 뿐이고, 품질이 저절로 오른다고 보장하지 않습니다.

```bash
node scripts/check-failure-patterns.mjs check --input 후보.json --log hb/failure-log.jsonl
node scripts/check-failure-patterns.mjs add --entry 기록.json --log hb/failure-log.jsonl
node scripts/check-failure-patterns.mjs validate --log hb/failure-log.jsonl
```

로그 경로는 `--log`, 환경변수 `HB_FAILURE_LOG`, `hb/failure-log.jsonl` 순서로 정합니다. **저장소에는 실패 사례를 넣지 않았습니다.** 처음에는 비어 있고, 파일이 없어도 동작합니다. 이때는 "대조하지 못했다"고 알리며, 경고가 없는 것을 안전하다는 뜻으로 쓰지 않습니다.

로그에는 미공개 기획이 들어갈 수 있습니다. `hb/failure-log.jsonl` 은 `.gitignore` 에 넣어 두었으니 공개 저장소에 올리지 마세요. 스킬에서는 `~/.claude/hb/failure-log.jsonl` 처럼 도구별 사용자 폴더에 둡니다.

### 로그 형식

한 줄에 기록 하나를 JSON으로 적습니다. 아래 형식에서 꺾쇠 부분을 사람이 채웁니다.

```json
{
  "id": "<겹치지 않는 번호>",
  "recorded_at": "YYYY-MM-DD",
  "recorded_by": "<기록을 확인한 사람>",
  "kind": "오발제",
  "industry": "<업종>",
  "yama": "<당시 야마 한 문장>",
  "failure_tags": ["<아래 실패 유형>"],
  "metrics": ["<템플릿의 지표 id>"],
  "entities": ["<기업 이름>"],
  "what_went_wrong": "<무엇이 틀렸는지 사실로>",
  "lesson": "<다음에 확인할 것>",
  "evidence": [{ "title": "<정정·반박 자료 제목>", "url": "https://...", "date": "YYYY-MM-DD" }]
}
```

- `kind` 는 `오발제` 또는 `실패 기획`입니다.
- `metrics`, `entities`, `evidence` 는 선택입니다. 나머지는 필수입니다.
- `recorded_by` 에 `claude`, `gpt`, `ai` 같은 값을 넣으면 거부합니다. 사람이 확인한 기록만 남기기 위해서입니다.

### 실패 유형 (`failure_tags`)

| 값 | 뜻 |
|---|---|
| `plan_as_actual` | 계획·전망을 실적처럼 썼습니다 |
| `basis_mismatch` | 기간·단위·범위가 다른 수치를 비교했습니다 |
| `macro_uncontrolled` | 거시 변수를 통제하지 않았습니다 |
| `seasonality` | 계절성을 놓쳤습니다 |
| `single_company_generalized` | 일부 기업 사례를 산업 전체로 넓혔습니다 |
| `press_release_echo` | 같은 보도자료를 독립 근거로 셌습니다 |
| `repeated_conclusion` | 이미 반복된 결론이었습니다 |
| `causation_assumed` | 원인을 확인 없이 단정했습니다 |
| `counter_ignored` | 반대 사례를 빠뜨렸습니다 |
| `lagging_misread` | 시차 효과(래깅 등)를 본업 변화로 읽었습니다 |
| `unit_misread` | 지표나 단위를 잘못 읽었습니다 |
| `source_unread` | 본문을 열지 않고 확정했습니다 |
| `other` | 기타 |

### 후보 입력과 대조 규칙

```json
{ "industry": "조선", "yama": "후보 야마 한 문장", "risk_tags": ["basis_mismatch"], "metrics": ["order_backlog"], "entities": ["기업 이름"] }
```

`yama` 만 필수입니다. 겹치는 점수는 다음과 같이 셉니다.

| 겹치는 것 | 점수 |
|---|---|
| 같은 업종(별칭 포함) | 2 |
| 같은 실패 유형 하나마다 | 3 |
| 같은 지표 하나마다 | 2 |
| 같은 기업 하나마다 | 2 |
| 야마 문장의 글자쌍 겹침 0.35 이상 | 3 |
| 야마 문장의 글자쌍 겹침 0.2 이상 | 1 |

합이 4점 이상이면 `유사`, 6점 이상이면 `강한 유사` 경고를 냅니다. 경고는 겹치는 이유와 당시 교훈을 보여 줄 뿐, 후보를 탈락시키지 않습니다. 문장 겹침은 글자 수준 비교라서 뜻이 같아도 표현이 다르면 놓칩니다. 그래서 `risk_tags` 와 `metrics` 를 함께 적을수록 대조가 정확해집니다.
